# 项目长期记忆

最后更新：2026-08-27

## 1. 本文件的作用

这是项目的长期事实来源。后续无论更换对话还是调整方案，都先阅读并更新本文件，避免遗忘题目限制、用户偏好和已经作出的决定。

## 2. 题目硬性要求

- 独立设计并实现一个编程智能体（coding agent），效果类似简化版 Claude Code、Codex、OpenCode 或 DeepSeek Harness。
- Agent 需要与大语言模型交互，并能自主读取和修改本地文件、执行本地命令、根据结果继续行动，最终完成真实编程任务。
- 功能多少不限，编程语言不限，运行时使用的模型不限。
- 不得给现成 Agent 产品套壳。
- 不得使用 Agent 框架或 Agent SDK，包括但不限于 LangChain、LlamaIndex、OpenAI Agents SDK、Claude Agent SDK、AutoGen、CrewAI。
- 可以使用模型厂商的普通 API 客户端库、OpenAI 兼容网关和模型原生 tool calling。
- 不得依赖 Code Interpreter、Files API 等服务端托管的代码执行或文件工具。
- 对话历史与上下文管理、工具定义和本地执行、模型输出解析、Agent 循环和终止条件、错误处理等核心逻辑必须自行编写。
- 可以使用 AI 辅助开发，但开发者必须对所有设计和代码负责，并能在面试中解释。
- API Key 只能通过环境变量或不入库的配置文件提供，不能出现在仓库、README.txt 或视频中；若泄露必须立即作废。
- 需要在题目发布后新建公开 GitHub/Gitee 仓库，保留完整提交历史，不压缩或改写已推送历史；截止后不得再推送。
- 截止时间：2026-09-02 24:00（北京时间 2026-09-03 00:00）。
- 提交物共三项：公开 Git 仓库、1000 汉字以内的 README.txt、2 分钟以内且不超过 200 MB 的 MP4 演示视频。
- 最终提交一个以本人姓名命名的 ZIP，ZIP 内只放 README.txt 和视频；仓库地址写在 README.txt 中。
- 面试会播放视频、介绍方案并答辩。重点是能否解释 Agent 的运行原理并为设计决策辩护。

原始题目文件：`../推免考核题目学生版.pdf`

## 3. 用户的长期要求

- 项目很重要，后续面试准备围绕本项目展开。
- 复杂度适中：不能只是最小玩具，也不能堆砌难以掌握的功能。
- 正式代码可以达到约 2000 到 3000 行，允许适度提高复杂度。
- 最终保留 2 到 3 个清晰、有证据、可演示的技术亮点，软件工程架构和模式需要成为亮点的一部分。
- 用户必须彻底理解每个代码细节；解释使用通俗中文，并持续解释到用户能够复述和处理追问。
- 不安排大段“先学后做”；采用写一个增量、解释一个增量、测试一个增量、追问一个增量的方式。
- 每增加一部分代码，再为这部分代码维护若干面试问题。问题必须绑定到具体增量、文件、符号和测试，不能只记录泛化问题。
- 所有未理解、未验证或待决定事项必须明确标记，不用模糊说法掩盖。
- 开发过程中优先选择“容易解释、容易测试、容易现场辩护”的方案，而不是炫技。

## 4. 第一版技术路线（待用户确认）

- 产品形态：命令行 Coding Agent。
- 语言：Python 3.11+。
- 总体架构：六边形架构（Ports and Adapters），核心遵循依赖倒置；外部模型、CLI、文件系统、进程和事件输出均作为 Adapter。
- 局部模式：Adapter/Gateway、Strategy、Observer、Command、Registry/Factory、责任链和显式有限状态机。只在解决真实问题时使用。
- 模型接入：使用普通 `openai` Python 客户端连接 DeepSeek；官方模型参数为 `deepseek-v4-pro`，base URL 为 `https://api.deepseek.com`。
- 环境变量：项目自行约定 `DEEPSEEK_API_KEY`、`DEEPSEEK_MODEL` 和 `DEEPSEEK_BASE_URL`。API Key 本身没有所谓“正确变量名”。
- 模型协议：第一版使用 Chat Completions 原生 function/tool calling。模型只提出工具调用，本地程序负责校验、执行并返回结果。
- 核心工具：列目录、读文件、精确文本替换、写新文件、搜索文本、执行命令。
- 代码组织：约 2000 到 3000 行正式代码，使用 `src` 布局、显式领域对象、手工依赖注入和可测试接口；避免异步、多进程和依赖注入框架。
- 测试：标准 `pytest`；模型调用使用 Fake Client 做可重复集成测试，另保留一次真实 API 冒烟测试。
- 兼容性：macOS、Linux、Windows；路径、命令执行、临时目录和终端输出必须使用跨平台方案，并通过 CI matrix 验证。

## 5. 三个候选亮点

### 亮点 A：工作区安全边界

所有文件路径都规范化并限制在指定 workspace 内；命令固定在 workspace 中运行，带超时、输出上限和高风险命令拦截。重点展示“Agent 能行动，但行动边界由宿主程序掌控”。

### 亮点 B：分层上下文压缩

永远保留系统规则、原始任务和最近交互；旧工具输出先做确定性截断，历史超过预算后再生成结构化摘要。重点展示长任务中如何控制上下文，同时避免忘记关键事实。

### 亮点 C：验证后完成与失败修复

跟踪文件是否被修改、修改后是否执行过验证。若模型过早宣布完成，宿主程序要求它先测试或检查；验证失败时把错误结果送回模型继续修复，并受最大步数约束。

## 6. 明确不做的内容

- 不做 Web 或桌面 GUI。
- 不做多 Agent 协作。
- 不做向量数据库、RAG、插件市场或 MCP 客户端。
- 不做远程代码执行。
- 不做自主 Git push、自动发布或部署。
- 第一版不做并行工具调用和异步 Agent 循环。
- 不展示或保存模型隐藏推理，只展示任务、工具调用、工具结果和最终答复。

## 8. 开发与教学规则

每新增一个模块或技术点，必须同时完成以下内容：

1. 用一句话说明它解决什么问题。
2. 画清输入、输出和调用关系。
3. 逐段解释实现，不保留“魔法代码”。
4. 列出正常路径、错误路径和边界条件。
5. 编写测试并解释测试为何足够。
6. 在面试题库中为本次代码增量增加至少 3 个问题，并绑定文件、符号、测试和 Git commit。
7. 让用户用自己的话复述；不能复述则换一种解释方式。
